### Версия 0.7.0 — Typed IR и Elaborator

Первый этап новой архитектуры реализован для поддерживаемых сигнатур.
Требование спецификации о известном типе абсолютно каждого узла ещё не выполнено:
неаннотированные определения и некоторые отложенные операции сохраняют неизвестный тип.

Реализовано:

- единый слой типов поверх существующего symbolic kernel;
- отдельный `Elaborator`;
- построение **Typed IR**, не смешанного с исходным `Term` DAG;
- явные узлы `Embed<Source, Target>` для безопасных неявных преобразований;
- скалярная башня `Nat -> Integer -> Rational -> Real -> Complex`;
- типизация бинарных операций и вызовов функций;
- сохранение `FunctionCall` в Typed IR до вычислительной beta-редукции;
- coercion аргументов функций;
- проверки типов для `Vector` и `Matrix`, включая размерности;
- ранняя диагностика несовместимых операций;
- публичный API получения и форматирования Typed IR.

Ключевой архитектурный принцип: обычное выполнение по-прежнему использует
существующий immutable `Term` DAG, а Typed IR является отдельным результатом
элаборации. Это позволяет развивать строгую математическую типизацию, не ломая
symbolic kernel и существующие normalizer'ы.

Также уже доступны математические имена `$alpha`/Unicode, полная форма
`function` с локальными определениями и завершающим `return`, типизированные
lambda нескольких аргументов и лексические замыкания. Эти части этапа 0.12
не следует считать будущей работой.

## 0.8.0 — Логика, предикаты и assumptions: реализованный фрагмент

### Цель

Добавлен слой математических утверждений для simplifier'а, normalizer'а и
условий переписывания. Теории и общие доказательства используют его в следующих этапах.

### Реализовано

- `Predicate` как отдельный тип IR;
- сравнения `=`, `!=`, `<`, `<=`, `>`, `>=` как математические предикаты;
- трёхзначная логика:
  - `True`;
  - `False`;
  - `Unknown`;
- структурное равенство `===`;
- математическое равенство `==`;
- `assume condition`;
- `assuming { ... } { ... }`;
- `AssumptionSet` внутри `Context`;
- логические операции `and`, `or`, `not`;
- локальная область видимости assumptions;
- query API для проверки предиката в текущем контексте;
- assumption-aware simplification.

### Проверенный пример

```text
parameter x : Real

simplify(sqrt(x^2))
```

сохраняет `sqrt(x^2)`, но:

```text
assuming {
    x >= 0
} {
    simplify(sqrt(x^2))
}
```

возвращает `x`.

### Выполненные критерии

- неизвестное утверждение никогда не интерпретируется как истинное;
- assumptions не выходят за границы своего контекста;
- simplifier может запрашивать доказуемость условий rewrite rules;
- `==` и `===` имеют различную семантику;
- ошибки области определения могут выражаться через предикаты, а не
  только через runtime diagnostics.

### Зависимости

Использует Typed IR 0.7. Нужен до реализации общей theory/proof system.

### Границы этапа и IDE

- `query` возвращает `True`, `False` или `Unknown`, без переносимого proof object.
  Существующее `prove` требует пустого контекста до этапа 0.10.
- Вывод ограничен точными сравнениями, нормальными формами, простыми границами
  одной величины и областью определения скалярных операций. Общего решателя нет.
- `domain(expression)` позволяет запросить определённость и использовать её
  как предположение; известные конфликты отклоняются с откатом всего ввода.
- `assume n:Integer`, предположения о свойствах, кванторы и разбор случаев пока
  не поддержаны. Алгоритмы анализа не используют контекст для выбора формул.
- `=` внутри условия обозначает равенство; обычный оператор `x=0` сохраняет
  синтаксис присваивания. Для однозначного сравнения используется `==`.
- IDE получила панель Assumptions, подсветку и автодополнение логики,
  отображение предикатов в математическом preview и просмотр типа Predicate.
- Формат IR версии 3 сохраняет предикаты; читает также версии 1 и 2.
  Экспорт модулей с активными предположениями отклоняется.

Контракт: [LOGIC.md](LOGIC.md). Пример: [logic.math](../examples/logic.math).
Проверка: 295 тестов, включая 32 новые проверки языка, API и IDE.

## 0.9 — Theory system, axioms и properties

- точные контрпримеры и статусы proved/disproved/unknown/assumed;

- библиотечные контракты Semigroup, Monoid, Group, Ring, Field;

Проверка: 364 теста. Пример: [theories.math](../examples/theories.math).

### Наследование и композиция (0.9.1)

- `theory Child<T> extends Parent<T>, Other<T>` с подстановкой параметров;
- наследование операций, констант и всех аксиом, включая несколько ветвей;

- диагностика несовместимых членов, разных одноимённых аксиом и локального переопределения;

Пример: [theory_inheritance.math](../examples/theory_inheritance.math).

реестр свойств. Использование
аксиом и условных сертификатов требует последующего этапа proof system.

### Синхронизация реализации и numeric (0.9.2)

- текущий переносимый формат — IR 7; версии 1–6 продолжают читаться;
- введён `ApproxNumber` и явный pipeline `expr |> numeric(digits)` для
  высокоточного приближения замкнутых вещественных выражений;
- `numeric` не меняет точную семантику `Number`, `simplify`, `normalize` и calculus;
- документация синхронизирована с уже существующими algebra backends:
  координатами, обращением, делением, отрицательными степенями и `analytic_lift`;
- `sqrt(q)` для не-квадратного положительного рационального `q` канонизируется
  как точная рациональная степень `q^(1/2)`, что устраняет расхождение форм записи
  в коэффициентах пользовательских алгебр.


### Цель

Сделать абстрактные математические структуры объектами самого языка, чтобы
`Group`, `Ring`, `Field`, `VectorSpace` и похожие конструкции реализовывались
в стандартной библиотеке, а не как специальные Python-классы ядра.

### Целевая область этапа (частично реализована)

- `theory Name<T> { ... }`;
- параметры типов теории;
- `operation` и сигнатуры операций;
- `const` внутри theory;
- `forall` и базовые кванторы;
- `axiom`;
- `implements`;
- проверку реализации theory конкретной структурой;
- `property` / traits;
- состояния свойства:
  - `assumed`;
  - `proved`;
  - `disproved`;
  - `unknown`;
- различие:

```text
assume multiplication associative
```

и

```text
prove multiplication associative
```

- хранение proof metadata для доказанных свойств.

### Первый библиотечный тест

```text
theory Semigroup<T> {
    operation (*) : T x T -> T

    axiom associative {
        forall a, b, c : T:
            (a*b)*c = a*(b*c)
    }
}
```

Затем:

```text
theory Monoid<T> { ... }
theory Group<T> { ... }
theory Ring<T> { ... }
theory Field<T> { ... }
```

### Критерии готовности

- theory компилируется в собственный IR;
- implementation проверяется по operation signatures и axioms;
- normalizer и proof engine могут безопасно запрашивать properties;
- `Ring`, `Group` и `Field` не требуют специальных веток parser/runtime.

### Зависимости

Typed IR 0.7 + predicates/assumptions 0.8.

## Сквозное направление — вывод формул и функции в конечномерных алгебрах

### Цель и границы

Автоматически строить формулы операций и вычислять встроенные функции в новых
алгебрах по их базису и relations, без отдельных реализаций для dual, complex
или quaternion. Разделить три результата: найденный кандидат формулы,
вычисленное значение и независимо проверенное доказательство.

Это направление выполняется инкрементами вместе с 0.10, 0.14 и 0.15. Первые
инкременты используют уже существующий Algebra Engine и не требуют завершения
0.11 или всех backend'ов 0.16. Ниже указана целевая последовательность;
реализация отдельного фрагмента не означает готовности всего инкремента.

Начальная область: конечномерные ассоциативные алгебры с единицей, проверенным
базисом и центральными скалярами над поддерживаемым полем. Для Taylor-переноса
нужны скаляры характеристики ноль и подходящий контракт скалярной функции.
Алгебры с непроверенным базисом и произвольные неассоциативные структуры требуют
отдельного обоснования применимости алгоритмов.

### F1 — Координаты, обратимость и деление — реализованный вычислительный слой

**Статус 0.9.2: в основном реализовано.** Старый roadmap описывал этот слой как
будущий, однако текущий `AlgebraNormalizer` уже предоставляет координаты по базису,
восстановление из координат, матрицы умножения, проверку обратимости, обращение,
деление и отрицательные целые степени. Символьные центральные коэффициенты
обрабатываются существующим coefficient backend и assumptions.

Рабочие классы примеров включают:

```text
algebra D over Real {
    generator eps
    relation eps^2 = 0
    derive basis
}

(a+b*D.eps)/(c+d*D.eps)
(1+D.eps)^-1
```

При доказанном `c != 0` первая формула сводится к координатному выражению
`a/c + (b*c-a*d)/c^2*D.eps`. Механизм не привязан к dual numbers: он работает
и с более высокими нильпотентами, а для некоммутативных алгебр сохраняет порядок
множителей. Критерий над поддерживаемым полем строится через матрицу умножения и
её determinant/adjugate; результат `Unknown` сохраняется, если необходимых условий
нельзя доказать.

**Осталось развить:** отдельный публичный conditional-formula object со списком
использованных assumptions, более широкий класс коэффициентных областей, явное
разделение левого и правого решения уравнений и переносимый proof certificate для
самого шага обращения. Это теперь задачи расширения F1, а не базовая реализация.

### F2 — Точный Taylor-перенос на нильпотентные расширения — частично реализован

**Статус 0.9.2: основной exact lift работает.** `mathlang/analytic_lift.py`
разлагает аргумент как `a+n`, проверяет нильпотентность `n` нормализацией и для
поддерживаемых функций строит конечную точную формулу
`sum(f^(k)(a)/k! * n^k)`. Индекс нильпотентности определяется из relations, а
не из имени алгебры. Поддерживаются `exp`, `sin`, `cos`; для вещественных
регулярных центров также `log` и `sqrt` при доказанной допустимости ветви.

Это работает для нескольких нильпотентных генераторов и для индексов выше двух.
Например, из `eps^2=0` автоматически получается
`exp(a+b*eps)=exp(a)+b*exp(a)*eps`, а для подходящей алгебры с несколькими
генераторами сохраняются смешанные члены вроде `p*q/2`.

**Осталось развить:** более общий контракт дифференцируемой/аналитической функции,
сертификат точности Taylor lift, расширение branch/domain анализа и связь с будущей
общей системой теорем. Обычный `TaylorSeries` с остатком по-прежнему не считается
точным значением функции сам по себе.

### F3 — Минимальный многочлен и общий расчёт функций — частичная специализация

Некоторые простые определяющие отношения уже распознаются напрямую. В частности,
если relation даёт `j^2=-1`, `analytic_lift` выводит
`exp(j*x)=cos(x)+j*sin(x)` без проверки имени `j`; масштабированный случай вроде
`r^2=-2` также сводится к синусу и косинусу с `sqrt(2)`. Нильпотентные relations
покрываются F2.

Общего алгоритма минимального многочлена пока нет. Следующий этап:

- находить линейные зависимости `1,z,z^2,...` в координатах алгебры;
- получать минимальный/аннулирующий многочлен в поддерживаемой области коэффициентов;
- строить `f(z)=r(z)` степени ниже многочлена через интерполяцию Эрмита или другой
  проверяемый finite-dimensional functional calculus;
- учитывать кратные корни, области определения и ветви;
- сохранять символическое значение, если закрытая форма не поддерживается.

Явное приближение теперь отделено от этой задачи: `numeric` уже умеет вычислять
замкнутые **вещественные скалярные** выражения с заданной точностью, но общий
численный backend для координат произвольной алгебры и строгая оценка ошибки ещё
не реализованы.

### F4 — Формальные ряды и проверяемые аналитические тождества — частично реализовано

Формула Эйлера для квадратичного relation уже получается вычислительным
`analytic_lift`, поэтому она больше не является приёмочным критерием будущей
реализации. Не реализована, однако, общая доказательная инфраструктура бесконечных
рядов. Требуется:

- ввести формальные степенные ряды отдельно от конечных сумм и `TaylorSeries`;
- выводить рекуррентные соотношения коэффициентов из relations;
- доказывать равенство коэффициентов для всех индексов, а не конечного префикса;
- явно учитывать сходимость и допустимость перестановки бесконечных операций;
- поддержать альтернативные сертификаты через ОДУ, начальные условия и теоремы
  единственности.

В некоммутативном анализе порядок множителей должен сохраняться, например
`d(z(x)^2)/dx = z'(x)*z(x) + z(x)*z'(x)`. Текущий algebra calculus не даёт права
автоматически применять коммутативные рекуррентные формулы без соответствующего
свойства.

### F5 — Условные сертификаты и вывод в абстрактных теориях

- оформлять координатное решение, обратимость, нильпотентность, перенос
  функции и распознавание ряда как проверяемые шаги proof system 0.10;
- включать исходную алгебру, условия на коэффициенты и ветви функций,
  использованные axioms и теоремы в переносимый сертификат;
- проверять сертификат без повторного поиска формулы и отвергать потерю
  assumptions при сохранении, импорте или применении результата;
- отделить нормализацию выражений в конкретной алгебре от применения аксиом
  и ранее доказанных теорем в абстрактной структуре;
- задавать аналитический смысл `exp`, `sin` и других функций отдельными
  контрактами: одни аксиомы кольца этот смысл не определяют;
- ограничить автоматический поиск заявленными классами задач и бюджетом,
  сохраняя `unknown` при отсутствии доказательства.

### Связь с существующими этапами

- **0.10:** условные сертификаты и применение общих теорем;
- **0.13:** примеры новых алгебр и контрактов в стандартной библиотеке;
- **0.14:** общий точный линейный решатель и матрицы умножения;
- **0.15:** производные, формальные ряды, ветви и функциональное исчисление;
- **0.16:** расширение классов relations, для которых доступны проверенные
  базисы и надёжная нормализация.

Backend'ы нормализации дают вычислительную основу, но не заменяют постановку
уравнений, решение в координатах и аналитические правила переноса функций.

## 0.10 — Общая система доказательств

### Цель

Перейти от нескольких специализированных вычислительных proof certificate к
общему проверяемому языку доказательств.

### Реализовать

- `theorem`;
- `proof { ... }`;
- `Goal`;
- `Proof`;
- `ProofStep`;
- применение axioms;
- применение ранее доказанных theorems;
- rewrite step;
- normalization step;
- symmetry / transitivity / reflexivity;
- использование локальных assumptions;
- proof by finite basis для существующих algebra proofs через общий API;
- разделение:
  - `ProofSearch`;
  - `ProofChecker`;
- строгий независимый checker;
- перечисление всех использованных axioms и assumptions в proof object;
- сериализацию proof tree;
- условные сертификаты автоматически выведенных формул, включая координатное
  обращение элементов алгебры и проверяемые правила переноса функций (F1-F5).

### Целевая модель

```text
ProofSearch
    -> Proof
    -> ProofChecker
```

Поиск может быть эвристическим и сложным. `ProofChecker` должен оставаться
маленьким, строгим и составлять доверенную границу системы.

### Критерии готовности

- успешное `prove` возвращает полноценный `ProofResult`;
- сохранённый proof tree можно проверить без повторного proof search;
- proof object точно фиксирует зависимость от axioms;
- ложный или повреждённый proof tree отвергается checker'ом.

### Зависимости

0.8 и 0.9.

## 0.11 — Параметрические и индексированные алгебры

### Цель

Расширить текущий Algebra Engine до семейства алгебр, задаваемых индексированными
генераторами и условными relations.

### Реализовать

- параметры algebra;
- индексированные generators:

```text
generator e[i] for i in 1..n
```

- многомерные generators:

```text
generator E[i,j]
    for i in 1..n
    for j in 1..n
```

- индексные переменные и диапазоны;
- conditional relations:

```text
e[i] * e[j] = -e[j] * e[i]
    when i != j
```

- pattern matching по индексам;
- условия над индексами;
- параметрический `AlgebraDefinition`;
- `derive basis`;
- `assert basis`;
- регистрацию domain-specific normalizer'ов;
- диагностику неизвестной termination/confluence.

### Главный тест этапа

Полностью выразить средствами языка:

```text
algebra Clifford(p : Nat, q : Nat) over Real {
    generator e[i] for i in 1..p+q

    relation {
        e[i] * e[j] = -e[j] * e[i]
            when i != j

        e[i]^2 = 1
            when i <= p

        e[i]^2 = -1
            when i > p
    }

    multiplication bilinear
    derive basis
}
```

### Критерии готовности

- `Clifford(p,q)` не имеет специальных runtime-классов;
- basis строится автоматически хотя бы для ограниченного конечного класса;
- conditional relation корректно матчится и проверяет условие;
- невозможность доказать завершимость явно отражается в diagnostics.

### Зависимости

0.9 theory/properties и 0.10 proof infrastructure.

## 0.12 — Пользовательские операции, операторы и расширенные функции

- перегрузку операций через Typed IR;
- пользовательские infix/prefix operators;

- пример:



## 0.16 — Продвинутые backend'ы нормализации

### Цель

Перейти от локальных rewrite systems к специализированным алгоритмам для
важных классов алгебр.

### Планируемые backend'ы

1. **Canonical polynomial normalizer:** развить уже реализованную точную
   полиномиальную нормализацию; выделить общий контракт коэффициентов,
   каноничности и сертификатов. Базовый вариант не является полностью будущей
   работой.
2. **Commutative Groebner basis:** нормальные формы по идеалам, исключение
   переменных и поддерживаемые полиномиальные задачи с условиями на параметры.
3. **Ограниченный Knuth-Bendix completion:** построение правил и обработка
   критических пар в явно выбранных эквациональных теориях; завершение
   completion не гарантируется.
4. **Noncommutative Groebner basis:** расширение нормализации ассоциативных
   алгебр с некоммутативными полиномиальными relations.
5. **Groebner-Shirshov methods:** методы для выбранных категорий алгебр,
   включая перспективную поддержку алгебр Ли. Этот пункт пересекается с
   некоммутативными базисами Groebner и не обозначает универсальный следующий
   уровень; для каждой категории нужны собственные контракты и сертификаты.

Первые задачи F1-F2 используют существующую нормализацию и точную линейную
алгебру. Эти backend'ы расширяют область автоматического вывода, но сами по
себе не выводят аналитические тождества и не определяют встроенные функции
для произвольной новой теории.

### Общий API

Каждый backend должен работать через общий `Normalizer` и публиковать metadata:

```text
termination: known / unknown
confluence: known / unknown
```

### Безопасность вычисления

- лимиты количества rewrite steps;
- detection циклов;
- timeout/budget API;
- diagnostics при недоказанной confluence;
- никакое недоказанное предположение о canonical form не должно автоматически
  превращаться в доказательство равенства.

### Критерии готовности

- backend можно заменить без изменения AST/Typed IR;
- proof engine может различать каноническую нормализацию и эвристическое
  simplification;
- результаты normalizer'а имеют достаточную информацию для proof certificate.

### Зависимости

Generic algebra + proof system.

# Зависимости этапов

Основная последовательность:

```text
Typed IR [0.7, готово]
        |
        v
Logic / Assumptions [0.8, ограниченный фрагмент готов]
        |
        v
Theories / Properties [0.9]
        |
        v
General Proofs [0.10]
        |
        v
Generic Algebra [0.11]
        |
        +--------------------+
        |                    |
        v                    v
Operators / Functions     Composite Values
[0.12]                  [0.14]
        |                    |
        +----------+---------+
                   |
                   v
             Standard Library
                [0.13+]
                   |
                   v
          Advanced Mathematics
              [0.15-0.16]
                   |
                   v
        Tooling / IDE / Stabilization
              [0.17-1.0]
```

Ключевой принцип разработки: **не добавлять новую математическую сущность как
специальный объект ядра, если её можно выразить через общие `Type`, `Theory`,
`Operation`, `Relation`, `Rewrite`, `Normalizer`, `Proof` и `Context`.**

Оптимизированные backend'ы допустимы, но должны менять только внутреннее
представление и производительность, а не математическую семантику.

Сквозное направление F1-F5 теперь начинается с уже работающих F1 и значительной
части F2, а оставшиеся proof/functional-calculus части постепенно подключают
инфраструктуру 0.10, 0.14 и 0.15. Линейная
схема выше задаёт основные зависимости языка, но не требует откладывать
обращение элементов и точные нильпотентные функции до завершения этапа 0.16.
