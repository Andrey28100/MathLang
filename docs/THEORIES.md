# Теории и проверка реализаций — 0.9.1

Этап вводит исполняемый фрагмент theory system: общие контракты, типизированные
аксиомы, конкретные реализации и проверяемые результаты. Имена Semigroup, Monoid,
Group, Ring и Field определены в стандартной библиотеке, а не в Python-ядре.
Общий язык доказательств и автоматический вывод произвольных аксиом остаются
следующими этапами.

Версия 0.9.1 расширяет этот фрагмент наследованием и композицией контрактов.

## Контракт и реализация

```text
theory Monoid<T> {
    operation (*) : T x T -> T
    const identity:T
    axiom associative {
        forall a,b,c:T: (a*b)*c = a*(b*c)
    }
    axiom identity_rule {
        forall a:T: a*identity = a and identity*a = a
    }
}

implementation Addition implements Monoid<Real> {
    operation (*) = (a:Real,b:Real)=>a+b
    const identity = 0
}
Addition.valid                         // True
Addition.associative                   // Property associative: proved
Addition.multiply(2,3) |> simplify      // 5
```

В сигнатуре операции можно использовать `x` или `×`. Поддерживаются имена
операций (`operation combine : T x T -> T`) и арифметические обозначения
`(+)`, `(-)`, `(*)`, `(/)`, `(^)`. Число аргументов проверяется; перегрузка
одного обозначения по нескольким сигнатурам пока не вводится.

Теория принимает от одного до восьми параметров типа. Они имеют собственные
номинальные идентичности и не становятся глобальными типами. В сигнатурах
допускаются эти параметры, встроенные скаляры, Predicate и составные типы
Function/Vector/Matrix/Series. Есть несколько параметров, например
`theory Action<T,K> {operation act:T x K -> T}`. Конкретная реализация передаёт
все аргументы: `implementation Scale implements Action<Real,Nat> { ... }`.

Каждая константа в теории имеет тип и не имеет значения. Каждая аксиома должна
содержать явный предикат; объявление одного имени аксиомы без тела отклоняется.
Тела могут ссылаться на связанные переменные и объявленные члены теории.
Обычная арифметическая запись внутри аксиомы обозначает соответствующую
объявленную операцию, а не заранее выбранное сложение или умножение скаляров.

Реализация связывает каждую операцию и константу ровно один раз. Лишние члены,
ошибки числа аргументов и несовместимые типы отклоняются атомарно. Для операций
подходят lambda, ранее определённые функции и символы с полной сигнатурой.
Начальные буквы имени не определяют математические свойства структуры.

Доступ к операциям через точку использует следующие имена:

| Объявление | Член реализации |
| --- | --- |
| бинарный `(+)` | `add` |
| бинарный `(-)` | `subtract` |
| унарный `(-)` | `negate` |
| унарный `(+)` | `positive` |
| `(*)` | `multiply` |
| `(/)` | `divide` |
| `(^)` | `power` |
| именованная операция | исходное имя |

Все имена членов должны быть различны, включая имена аксиом. `valid` и имена,
начинающиеся с `_total_`, зарезервированы для отчёта. Объявления теории и
реализации можно импортировать, помещать в namespace, сохранять и передавать
под псевдонимами. Они неизменяемы; `with/use` для реализации не добавлены.

## Проверка обязательств

Одной сигнатуры недостаточно: для каждой операции создаётся обязательство
`_total_name`, проверяющее определённость её тела на всём заявленном типе
аргументов. Для констант также проверяется область определения. Поэтому
`(x:Real)=>1/x` не считается полной операцией Real → Real даже у теории без
аксиом. Символическая функция с известной сигнатурой сохраняет неизвестную
полноту, пока нет сведений о её теле.

После подстановки конкретных операций каждая аксиома получает отдельный
`PropertyResult`:

| Статус | Смысл |
| --- | --- |
| `proved` | Обязательство проверено поддерживаемым точным методом |
| `disproved` | Сохранён конкретный допустимый контрпример |
| `unknown` | Текущий алгоритм не установил ответ |
| `assumed` | Пользователь явно принял аксиому внутри реализации; доказательства нет |

`Implementation.valid` возвращает True, только когда **все** обязательства
имеют статус proved. Наличие disproved даёт False; unknown или assumed при
отсутствии опровержения дают Unknown. Неудачная математическая проверка
сохраняется как отчёт кандидата; она не регистрирует доказанную структуру.

```text
import std.theories {Semigroup}
implementation Subtraction implements Semigroup<Real> {
    operation (*)=(a:Real,b:Real)=>a-b
}
Subtraction.valid                      // False
Subtraction.associative                 // контрпример a=0, b=0, c=1
Subtraction.associative.disproved       // True
Subtraction.associative.statement       // исходное утверждение с подстановками
```

Для свойства доступны `.statement`, `.proved`, `.disproved`, `.unknown`,
`.assumed`. Последние четыре — предикаты о статусе отчёта. Сам отчёт не
является предикатом и не превращается в True автоматически.

Точные доказательства аксиом поддержаны для полиномиальных равенств и их
конъюнкций. Поддерживаются суммы, произведения, унарные знаки, положительные
целые степени и деление на ненулевую числовую константу. Нулевые степени с
возможным основанием 0, произвольное деление и непрозрачные вызовы не
включаются в этот фрагмент. Результат хранит существующие сертификаты Proof.

Для имеющейся фактор-алгебры с проверенным конечным базисом каждую связанную
переменную заменяют общей линейной комбинацией базисных элементов с независимыми
символическими коэффициентами. Полученные равенства проверяет AlgebraNormalizer
и отдельный ProofChecker. Это доказательство для всех элементов алгебры,
а не только перебор нескольких базисных значений. Так пример проверяет
ассоциативность и дистрибутивность кольца кватернионов.

Опровержение использует ограниченный поиск точных свидетелей: 0,1,2 для Nat,
0,1,−1,2 для остальных скаляров; 0 и элементы базиса для фактор-алгебры.
Контрпример проверяется арифметикой. Если все рассмотренные значения подходят,
это **не** доказывает аксиому. Лимит `max_quantifier_checks` равен 128 на поиск;
перебор применяется не более чем к восьми связанным переменным. Дополнительно
действуют лимиты размера выражения, нормализации и точных чисел.

## Наследование и композиция

```text
import std.theories {Monoid, Semigroup}

theory Commutative<T> extends Semigroup<T> {
    axiom commutative { forall a,b:T: a*b = b*a }
}
theory CommutativeMonoid<T> extends Monoid<T>, Commutative<T> {}

implementation Addition implements CommutativeMonoid<Real> {
    operation (*) = (a:Real,b:Real)=>a+b
    const identity = 0
}
Addition.valid                          // True
Addition.associative.proved              // True: требование Semigroup
Addition.commutative.proved              // True: требование Commutative
```

Родители перечисляются после `extends` через запятую. Каждый должен быть уже
объявленной или импортированной теорией; допустимо квалифицированное имя.
Передаются все параметры типа. Они могут ссылаться на параметры дочерней
теории, встроенные типы и составные типы, разрешённые в сигнатурах теорий.
Часть аргументов можно зафиксировать или изменить их порядок:

```text
theory Action<T,K> {
    operation act:T x K -> T
    const identity:K
    axiom unit { forall a:T: act(a,identity)=a }
}
theory NaturalAction<T> extends Action<T,Nat> {}
implementation Scale implements NaturalAction<Real> {
    operation act=(x:Real,k:Nat)=>x*k
    const identity=1
}
Scale.valid                             // True
```

Подстановка действует на сигнатуры операций, константы и типы связанных
переменных в аксиомах. Родительский объект остаётся неизменным; дочерняя теория
получает собственные символы операций. Её локальные аксиомы видят все
унаследованные операции и константы. Параметры не попадают во внешнюю область.

Правила объединения:

- Совпадающие операции объединяются при одинаковых имени, обозначении и точной
  специализированной сигнатуре. Одноимённые константы требуют одинакового типа.
- Одноимённые аксиомы объединяются при одинаковой структуре после подстановки
  типов и операций. Имена связанных переменных могут различаться. Произвольная
  математическая эквивалентность для этого не доказывается.
- Разные сигнатуры, обозначения или одноимённые законы вызывают ошибку.
  Конфликты между именами операций, констант и аксиом также запрещены.
- Локальное повторное объявление унаследованного члена запрещено, даже если
  его сигнатура совпадает. Один и тот же непосредственный родитель с теми же
  аргументами не может быть указан дважды.
- В каждой группе членов сначала идут унаследованные объявления в порядке
  родителей, затем локальные. Проверяются определённость всех операций и
  констант, затем аксиомы. Общий предок через несколько ветвей не добавляет
  повторных требований.

Поэтому CommutativeMonoid получает Semigroup через Monoid и Commutative,
но требует одну операцию умножения и одну аксиому ассоциативности. Реализация
связывает каждый итоговый член один раз и проверяет все итоговые обязательства.
`assume` может назвать унаследованную аксиому по тем же правилам, что и локальную.
Наследование не превращает assumed/unknown в proved и не добавляет глобальные
предположения.

Стандартная библиотека использует цепочки Semigroup → Monoid → Group и
Ring → Field. CommutativeSemigroup расширяет Semigroup, CommutativeMonoid
объединяет Monoid и CommutativeSemigroup, AbelianGroup — Group и
CommutativeMonoid. Все контракты записаны на MathLang.

Глубина иерархии ограничена `Limits.max_theory_depth` (по умолчанию 32, корневая
теория имеет глубину 1). Общие предки учитываются один раз при проверке размера,
а глубина определяется самым длинным путём. Бюджеты `max_nodes` и `max_steps`
также ограничивают иерархию, специализацию и сравнение аксиом. Циклы и ссылки
вперёд отклоняются. Ошибка объявления откатывает текущий ввод целиком.

Это наследование контрактов. Переименование операций, перегрузки, локальные
переопределения и автоматические приведения между объектами Implementation
пока не поддерживаются.

## Предположения и граница доверия

```text
import std.theories {Semigroup}
combine:Function<Real,Real,Real>
implementation Candidate implements Semigroup<Real> {
    operation (*)=combine
    assume associative
}
Candidate.associative.assumed            // True
Candidate.valid                         // Unknown
```

`assume` в таком блоке называет аксиому выбранной теории. Установленное
опровержение нельзя заменить предположением; полнота операций также не может
быть принята через этот синтаксис. Предположенные аксиомы не становятся
rewrite rules и не влияют на глобальные assumptions или нормализатор.
Компиляция реализации при активном условном контексте отклоняется: текущие
переносимые сертификаты не фиксируют такие условия.

При загрузке проверяются исходный контракт, сигнатуры связываний и полный
набор конкретных обязательств. Checker заново строит цели из теории и
проверяет каждый сертификат или контрпример. Замена статуса, операции или
цели, чужой сертификат и удаление обязательства отклоняются. Проверка не
запускает ProofSearch. Формат IR 7 хранит теории, родителей с аргументами типов,
реализации, кванторы, отчёты и необходимые представления алгебр; читаются прежние
версии 1–6. Теория версии 5 загружается с пустым списком родителей.

Для каждой дочерней теории читатель заново специализирует родительские
сигнатуры и аксиомы и сверяет полный унаследованный состав. Удаление или
изменение требования при сохранённых родительских контрактах отклоняется.
Общие предки сохраняют разделяемые узлы DAG. Сохранённую теорию можно
импортировать и расширить без исходников родительских модулей.

## Самостоятельный forall

```text
P=forall x:Real: x^2 >= 0
query(P)                               // True
query(forall x:Real: x > 0)             // False
query(forall x:Real: x/x = 1)           // Unknown: область определения
```

Квантор имеет тип Predicate. Допустимы `forall a,b:T: ...`, отдельные группы
типов `forall a:T,k:Nat: ...` и последовательные вложенные forall. Переменные
локальны, обязательны аннотации; подстановка не захватывает их идентичности.
В запросе используются только внешние предположения, не ссылающиеся на связанные
переменные. Поиск ограничен простым фрагментом: тело проверяется символически,
затем ищется опровержение. Неинтерпретированные типы и вложенные кванторы под
логическими связками могут оставаться Unknown. Exists, инстанцирование общих
аксиом из контекста и автоматическое доказательство кванторных формул не добавлены.

## IDE, совместимость и дальнейшая работа

Панель **Properties** показывает реализации, обязательства, статусы и методы.
Столбец **Declared in** содержит имена теорий, впервые объявивших требование;
общий предок выводится один раз. Подсказка свойства содержит утверждение,
контрпример и происхождение, подсказка реализации — контракт с родителями.
Панель обновляется после Run/REPL,
сохраняется при откате ошибочного ввода и очищается при смене проекта.
Есть подсветка и автодополнение `extends` и других конструкций теории,
математический вывод ∀. Открыть панель
можно через View → Inspect properties или Ctrl+Alt+P.

Разрешённые скалярные вложения теперь действуют и на границе типизированного
вызова: например, 0 и 1 можно передать как элементы Quaternion. Для этого
нужно зарегистрированное представление алгебры, а тип скаляра должен входить
в её скалярное поле. В Typed IR сохраняется явный Embed. Различные номинальные
алгебры по-прежнему несовместимы.

Исполняемые примеры: [theories.math](../examples/theories.math) и
[theory_inheritance.math](../examples/theory_inheritance.math). Библиотека:
[std.theories](../mathlang/stdlib/theories.math). Проверки:
[test_theories.py](../tests/test_theories.py),
[test_theory_inheritance.py](../tests/test_theory_inheritance.py).

Этап 0.9 реализован частично; проверяемые контракты и их наследование готовы.
Вместо изменения объявления существующей алгебры используется отдельный
`implementation Name implements Theory<Type>`. Синтаксис спецификации
`algebra A implements Ring<A>`, общий property/traits-реестр,
использование аксиом в proof search, условные сертификаты и общие proof-блоки
остаются будущей работой. Field уже можно объявить как контракт; его условные
законы обратного элемента пока выходят за полиномиальный проверяющий фрагмент.
